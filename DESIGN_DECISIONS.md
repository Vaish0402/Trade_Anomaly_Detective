Architectural Overview
    ·The system follows a Three-Tier Filtering Pipeline. The core design principle is computational efficiency: we use low-cost        deterministic rules and statistical methods to filter the bulk of the data (250+ rows), escalating only the most complex semantic cases to the LLM.

Layer 1: Rule-Based Detection
   · Method: Vectorized Boolean checks using Pandas.
   · Justification: This layer handles "hard" truths that require zero reasoning, such as Quantity x Price != Total. It provides   instantaneous results with 100% precision for data entry errors.

Layer 2: Statistical Detection
   · Method: Z-Score Analysis (Threshold: 3.0).
   · Justification: I chose Z-scores over IQR because it effectively highlights extreme outliers in relatively normal distributions of  unit prices and payment days.
   · The Precision Trade-off: My current report shows a precision of 0.06 with 68 False Positives.
        ·Decision: I intentionally kept the threshold sensitive to ensure a Recall of 1.0. In trade compliance, the cost of a "False ·Negative" (missing fraud) is significantly higher than the cost of a "False Positive" (manual review of a delayed payment).🧠 

Layer 3: LLM reasoning
   · Method: Prompt-based semantic validation via Groq (Llama-3.3-70B).
   · Justification: LLMs are used specifically for HS Code vs. Product Description checks, where a computer code (847130) might be assigned to a garment.
   · Constraint Fulfillment: To meet the "not lazy" constraint, only rows flagged by Layers 1 and 2 are sent for LLM reasoning. This reduced our LLM API surface from 250+ potential calls to just 73 targeted calls, saving ~70% in potential token costs.📁 

Output & Reporting
   · Anomaly Report: Structured with unique shipment_id keys and detailed evidence strings to assist human auditors.
   · Executive Summary: Generated by feeding the consolidated anomaly list back to the LLM. It translates technical Z-scores into business risks (e.g., "Liquidity issues") for an Operations Head.
   · Usage Tracker: Implemented a custom logging class to capture real-time input_tokens, output_tokens, and latency directly from the Groq API response.
